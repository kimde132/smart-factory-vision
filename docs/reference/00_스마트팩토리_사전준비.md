## 기존 계획서에서 바로잡을 기술 항목

기존 계획서의 FastAPI·백엔드 패키지 목록에 포함된 `psycopg`는 PostgreSQL용 드라이버이므로 이번 MSSQL 프로젝트에서는 사용하지 않는다.

MSSQL 연결은 다음 구성으로 통일한다.

```text
FastAPI
→ SQLAlchemy
→ pyodbc
→ Microsoft ODBC Driver 18 for SQL Server
→ Microsoft SQL Server
```

필요 패키지:

```text
sqlalchemy
pyodbc
alembic
```

사용하지 않을 패키지:

```text
psycopg
psycopg2
```

# 2. 프로젝트를 직접 이해한 내용

## 2.1 왜 만드는가?

스마트팩토리 분야의 AI 비전 검사 직무 취업을 준비하기 위해 프로젝트를 진행한다.

실제 스마트팩토리의 모든 구성 요소를 6주 안에 구현할 수는 없으므로, 공장의 비전 검사 장비 한 대가 수행하는 핵심 흐름을 축소하여 구현한다.

구현하려는 핵심 과정은 다음과 같다.

- WPF로 검사 조작 화면 만들기
- 웹캠과 같은 외부 이미지 입력 장치로 이미지 촬영하기
- 촬영한 이미지를 AI 모델로 분석하기
- 우선 객체 탐지를 통해 볼트·너트·와셔의 개수를 확인하기
- 분석 결과를 WPF 화면에 표시하기
- 검사 결과를 Microsoft SQL Server에 저장하기
- 저장한 검사 이력을 조회하기
- DB에 저장된 데이터를 Excel로 추출하기

프로젝트의 중심은 WPF 화면 디자인이 아니라 다음 과정이다.

```text
직접 데이터 수집
→ 직접 라벨링
→ YOLO 파인튜닝
→ 성능 평가
→ 실패 사례 분석
→ 데이터 보완
→ 재학습
→ 실제 검사 프로그램과 연결
```

---

## 2.2 무엇을 검사하는가?

나무 트레이 위에 배치된 다음 부품을 검사한다.

- 볼트
- 너트
- 와셔

1차 범위에서는 각 부품이 미리 정한 수량만큼 존재하는지 검사한다.

시간이 충분히 남을 때만 다음 기능을 추가로 검토한다.

- 부품 위치 검사
- 부품 방향 검사
- 스크래치 또는 흠집 검사
- 잘못된 부품 검사

이 기능들은 1차 프로젝트의 필수 범위가 아니다.

---

## 2.3 정상과 불량 기준

### 정상 기준

YOLO가 탐지한 볼트·너트·와셔의 개수가 미리 설정한 부품별 기준 수량과 모두 일치하면 `OK`로 판정한다.

### 불량 기준

탐지된 부품의 개수가 기준 수량보다 적거나 많으면 `NG`로 판정한다.

예시:

```text
기준 수량
- bolt: 1
- nut: 1
- washer: 1

탐지 결과
- bolt: 1
- nut: 1
- washer: 0

판정
- NG
- 누락 부품: washer 1개
```

# 3. AI와 검사 로직의 역할 구분

## 3.1 YOLO의 역할

YOLO는 이미지에서 객체를 탐지한다.

YOLO가 반환하는 주요 정보는 다음과 같다.

- 탐지한 객체의 클래스
- 탐지 위치인 Bounding Box
- 탐지 신뢰도인 Confidence
- 클래스별 탐지 개수

예시:

```text
bolt 1개 탐지
nut 1개 탐지
washer 0개 탐지
```

YOLO가 직접 `OK` 또는 `NG`를 결정하는 것은 아니다.

## 3.2 Python 검사 로직의 역할

Python으로 작성한 검사 함수가 YOLO 탐지 결과와 기준 수량을 비교하여 `OK` 또는 `NG`를 결정한다.

이 검사 로직은 FastAPI 애플리케이션 내부에 구현한다.

```text
YOLO
= 이미지에서 무엇이 몇 개 보이는지 탐지

Python 검사 로직
= 필요한 개수와 실제 탐지 개수를 비교하여 OK / NG 판정
```

초기 검사 규칙의 개념은 다음과 같다.

```python
required_counts = {
    "bolt": 1,
    "nut": 1,
    "washer": 1,
}
```

실제 구현에서는 단순한 `set`보다 클래스별 수량을 계산할 수 있는 `Counter` 또는 딕셔너리 방식을 사용한다.

# 4. 확정된 시스템 구조

## 4.1 FastAPI 서버와 AI 서버를 별도로 분리하지 않는다

초기에는 다음처럼 별도의 AI 서버를 만들지 않는다.

```text
WPF
→ FastAPI
→ 별도 AI 서버
→ FastAPI
→ WPF
```

6주 프로젝트에서는 FastAPI 애플리케이션 내부에서 YOLO 추론, 검사 판정, DB 저장을 함께 수행한다.

```text
WPF
  ↓ 이미지 전송
FastAPI 애플리케이션
  ├─ 이미지 수신
  ├─ YOLO 모델 추론
  ├─ 부품별 개수 계산
  ├─ OK / NG 판정
  ├─ 원본·결과 이미지 저장
  └─ MSSQL 검사 결과 저장
  ↓ JSON 응답
WPF 결과 표시
```

코드는 역할별 파일로 나눌 수 있지만 서버 프로세스는 하나로 시작한다.

예시:

```text
ai-server/
└── app/
    ├── main.py
    ├── api/
    │   └── inspections.py
    ├── services/
    │   ├── yolo_service.py
    │   └── inspection_service.py
    └── db/
        └── repository.py
```

`yolo_service.py`가 별도 파일이라는 것은 별도 AI 서버라는 뜻이 아니다.

---

## 4.2 전체 검사 흐름

1. 볼트·너트·와셔의 기준 수량을 설정한다.
2. 나무 트레이에 부품을 배치한다.
3. WPF 프로그램에서 검사 시작 버튼을 누른다.
4. WPF가 카메라의 현재 이미지를 캡처한다.
5. WPF가 이미지를 FastAPI 서버로 전송한다.
6. FastAPI 내부에서 YOLO 모델이 이미지를 분석한다.
7. YOLO가 부품별 클래스, 위치, 신뢰도와 개수를 반환한다.
8. Python 검사 로직이 탐지 개수와 기준 개수를 비교한다.
9. 검사 로직이 `OK` 또는 `NG`를 판정한다.
10. FastAPI가 검사 결과와 이미지 경로를 MSSQL에 저장한다.
11. FastAPI가 검사 결과를 WPF에 반환한다.
12. WPF가 결과, 누락 또는 과다 부품과 결과 이미지를 표시한다.
13. 사용자는 검사 이력을 조회한다.
14. 날짜와 결과 조건에 따라 Excel 파일을 추출한다.

# 5. 초기 부품 개수 결정

## 5.1 처음에는 각 1개로 시작한다

초기 파이프라인 검증 기준은 다음과 같다.

```text
bolt: 1
nut: 1
washer: 1
```

처음부터 여러 개를 사용하면 탐지 실패의 원인을 구분하기 어려워질 수 있다.

초기 단계의 목표는 난이도를 높이는 것이 아니라 다음 전체 흐름이 동작하는지 확인하는 것이다.

```text
데이터 촬영
→ 라벨링
→ YOLO 학습
→ 객체 탐지
→ 클래스별 개수 계산
→ OK / NG 판정
```

각 1개를 검사한다고 해서 프로젝트 전체가 단순한 것은 아니다. 프로젝트의 핵심 난이도와 가치는 다음에서 나온다.

- 직접 데이터 수집
- 촬영 조건 설계
- 라벨링 기준 수립
- Train·Validation·Test 분리
- Precision, Recall, mAP 분석
- 오탐과 미탐 분석
- 실패 조건 데이터 추가
- 모델 버전별 비교
- WPF·FastAPI·MSSQL 통합

## 5.2 최종 개수는 실물 확인 후 결정한다

부품과 트레이가 도착한 뒤 다음을 확인하여 최종 기준 수량을 결정한다.

- 트레이 크기
- 부품이 화면에서 차지하는 크기
- 부품 간 겹침 가능성
- 부품을 배치할 수 있는 공간
- 실제로 자연스러운 조립 키트 형태

최종 예시는 다음처럼 변경할 수 있다.

```text
bolt: 2
nut: 2
washer: 2
```

또는 부품별 수량을 다르게 구성할 수 있다.

```text
bolt: 2
nut: 2
washer: 4
```

현재는 최종 수량을 확정하지 않는다.

# 7. 카메라 변경에 대한 전략

카메라가 달라지면 해상도뿐 아니라 다음 특성도 달라진다.

- 화각
- 렌즈 왜곡
- 색감
- 자동 노출
- 화이트밸런스
- 초점
- 선명도
- 노이즈
- 이미지 압축
- 금속 반사 표현

YOLO가 이미지를 일정 크기로 변환하더라도 이러한 카메라별 이미지 특성 차이는 남을 수 있다.

## 7.1 초기 단계

휴대폰 카메라로 다음을 진행한다.

```text
촬영 환경 설계
→ 파일럿 이미지 수집
→ 라벨링 연습
→ YOLO 초기 학습
→ 전체 학습 과정 확인
```

## 7.2 로지텍 웹캠 확보 후

```text
로지텍 웹캠으로 같은 조건 촬영
→ 휴대폰 데이터로 학습한 모델 테스트
→ 웹캠 환경 실패 사례 확인
→ 웹캠 이미지 추가 수집
→ 데이터셋 보완
→ 재학습
```

이 과정은 카메라 도메인 차이에 대한 실제 개선 사례로 포트폴리오에 활용할 수 있다.

## 7.3 데이터 폴더에 촬영 장치를 구분한다

```text
dataset/
└── raw/
    ├── phone_session_01/
    ├── phone_session_02/
    ├── webcam_session_01/
    └── webcam_session_02/
```

촬영 기록에도 카메라 정보를 남긴다.

```csv
session_id,camera,lighting,description
phone_01,smartphone,room_light,initial pilot dataset
webcam_01,logitech_webcam,room_light,deployment camera test
```

최종 테스트 데이터에는 실제 운영 장치인 로지텍 웹캠 이미지를 충분히 포함한다.

# 8. 촬영 환경 기본 원칙

초기에는 다양한 환경보다 통제된 환경에서 시작한다.

```text
카메라 위치 고정
촬영 거리 고정
트레이 위치 고정
조명 방향 고정
배경 고정
```

가능하면 트레이를 위에서 아래로 촬영하는 탑뷰를 사용한다.

```text
카메라
  ↓
트레이
```

탑뷰의 장점은 다음과 같다.

- 부품 형태가 비교적 일정하게 보임
- 부품 겹침을 줄이기 쉬움
- 촬영 거리를 고정하기 쉬움
- 추후 위치 검사로 확장하기 쉬움

## 8.1 파일럿 촬영의 목적

본격적으로 수백 장을 촬영하기 전에 15~30장의 파일럿 이미지를 촬영한다.

확인할 조건:

- 정상 상태
- 볼트 누락
- 너트 누락
- 와셔 누락
- 빈 트레이
- 부품이 가까이 붙은 상태
- 부품이 일부 겹친 상태

확인할 문제:

- 초점이 맞는가?
- 부품이 너무 작지 않은가?
- 금속 반사가 너무 심하지 않은가?
- 너트와 와셔가 사람 눈에도 구분되는가?
- 트레이 무늬가 객체 탐지를 방해하지 않는가?
- 그림자가 객체 형태를 가리지 않는가?

파일럿 이미지를 확인하기 전에는 대량 촬영과 본격적인 라벨링을 시작하지 않는다.

# 9. 교육장과 집에서 할 작업 분리

현재 평일 09시부터 18시까지 AI 교육을 받고 있다.

현재 수업은 Python 기초 중심이며, 이미 알고 있는 범위가 많아 강사님의 허락을 받아 필수 과제를 완료한 뒤 남는 교육 시간에 프로젝트를 진행할 수 있다.

# 12. 데이터셋 방향

## 12.1 직접 촬영한 데이터를 중심으로 사용한다

이번 프로젝트에서는 직접 구매한 트레이와 부품을 직접 촬영한 데이터를 주 데이터로 사용한다.

장점:

- 실제 검사 환경이 반영됨
- 데이터 수집 과정을 설명할 수 있음
- 라벨링 기준을 직접 만들 수 있음
- 실패 사례를 직접 재현할 수 있음
- 데이터 보완 후 성능 개선 과정을 보여줄 수 있음
- 기존 예제 실행이 아닌 개인 프로젝트가 됨

## 12.2 공개 데이터는 필수가 아니다

사전학습된 YOLO 모델 자체가 이미 일반적인 시각 특징을 학습한 상태이므로, 직접 촬영한 데이터로 파인튜닝을 시작할 수 있다.

```text
사전학습된 YOLO
+
직접 촬영한 볼트·너트·와셔 이미지
=
프로젝트 환경에 맞는 파인튜닝 모델
```

공개 데이터는 라이선스와 촬영 환경을 확인한 뒤 보조 데이터로만 검토한다.

```text
현재 프로젝트 정의와 결정 사항은 전달한 MD 문서를 기준으로 한다.

2. 왜 변경해야 하는지

→ 오류 수정
→ Git 커밋
→ README 또는 관련 문서 갱신
```

## 15.4 AI 생성 코드를 그대로 사용하지 않는다

각 코드에 대해 최소한 다음을 설명할 수 있어야 한다.

- 이 파일은 왜 존재하는가?
- 이 함수의 입력과 출력은 무엇인가?
- 실행 흐름에서 언제 호출되는가?
- 실패하면 어떤 오류가 발생할 수 있는가?
- 어떤 라이브러리를 왜 사용하는가?
- 이 코드는 프로젝트의 어느 기능을 담당하는가?

Claude에게 코드를 요청할 때 코드 전체를 한꺼번에 생성하기보다, 파일과 기능 단위로 설명을 함께 요청한다.

# 20. 첫 주 작업 방향 요약

## 1단계: 프로젝트와 촬영 규칙 확정

- 프로젝트 저장소 생성
- 검사 기준 문서화
- 촬영 환경 확인
- 라벨 클래스 확정

## 2단계: 파일럿 데이터

- 15~30장 촬영
- 이미지 품질 검토
- 10~30장 라벨링
- 라벨링 기준 수정

## 3단계: 본 데이터 수집 시작

- 촬영 세션별 이미지 수집
- 정상·불량 조건 균형 확인
- 데이터 메타데이터 기록

## 4단계: 데이터셋 구성

- Train·Validation·Test 분리
- 같은 촬영 세션의 유사 이미지가 Train과 Test에 섞이지 않도록 관리
- `data.yaml` 작성

## 5단계: 시험 학습

- 1~3 Epoch Smoke Test
- 데이터 경로 확인
- 라벨 형식 확인
- 클래스 번호 확인
- 학습 코드 정상 실행 확인

첫 주에는 높은 모델 성능보다 데이터 파이프라인이 정상 동작하는 것이 중요하다.

# 21. 프로젝트 진행 원칙

1. 프로젝트의 중심은 AI 모델 튜닝과 개선 과정이다.
2. 매주 실제로 실행되는 결과물을 만든다.
3. 처음부터 완벽한 구조를 만들지 않는다.
4. 기능을 작은 단위로 구현하고 바로 실행한다.
5. 실패 사례를 숨기지 않고 개선 근거로 사용한다.
6. 데이터 촬영 조건과 모델 버전을 기록한다.
7. AI 도구가 만든 코드를 이해하지 못한 채 대량으로 추가하지 않는다.
8. WPF 화면 디자인에 지나치게 많은 시간을 사용하지 않는다.
9. PLC, 아두이노, 컨베이어, Unity와 C++는 1차 범위에서 제외한다.
10. 위치·흠집·스크래치 검사는 전체 필수 기능을 완성한 뒤 검토한다.
11. 기존 계획서와 결정 문서를 기준으로 구조의 일관성을 유지한다.
12. 매 작업 단위가 끝날 때 Git 커밋과 문서 갱신을 함께 한다.
