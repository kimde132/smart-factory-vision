# 1. 현재 상황과 프로젝트를 시작하는 이유

현재 AI 직무 취업을 목표로 준비하고 있으며, 포항에서 포스코 AI 부트캠프 교육을 받고 있다.

강사님과 진로 상담을 진행한 결과, 스마트팩토리 분야 중에서도 **AI 비전 검사 직무**를 준비해보는 방향을 추천받았다.

처음에는 다음과 같이 실제 생산라인 전체를 구현하는 프로젝트로 이해했다.

- 실제 컨베이어 벨트
- 아두이노
- PLC
- 센서
- 카메라
- AI 비전 모델
- WPF 조작 화면
- 데이터베이스
- 생산 데이터 관리

하지만 약 1개월 반이라는 기간 안에 이 모든 것을 새롭게 학습하고 구현하는 것은 현실적으로 어렵다.

따라서 실제 설비를 모두 구현하는 대신, **공장의 한 검사 공정을 소프트웨어로 축소하여 표현하는 프로젝트**로 범위를 조정한다.

이 프로젝트의 목적은 스마트팩토리 전체를 만드는 것이 아니다.

> **웹캠으로 제품을 촬영하고, 직접 튜닝한 AI 비전 모델이 부품 누락이나 불량을 판정하며, WPF 프로그램에서 검사 과정을 조작하고 결과를 확인한 뒤 Microsoft SQL Server에 검사 이력을 저장하는 시스템을 구현한다.**

이를 통해 단순히 YOLO 모델을 학습해보는 데서 끝나지 않고, AI 모델이 실제 검사 프로그램과 업무 데이터로 연결되는 전체 흐름을 경험하는 것이 목표다.

# 3. 프로젝트 한 줄 정의

> **웹캠으로 조립 트레이를 촬영하고 YOLO 모델로 필수 부품의 존재 여부를 검사한 뒤, WPF 화면에 정상·불량 결과를 표시하고 Microsoft SQL Server에 검사 이력을 저장하며 Excel 보고서로 추출할 수 있는 AI 비전 검사 시스템**

검사 대상은 현재 다음과 같이 가정한다.

- 조립 트레이
- 볼트
- 너트
- 와셔

정상 제품은 필수 부품이 모두 존재하는 경우다.

불량 제품은 다음과 같이 정의할 수 있다.

- 볼트 누락
- 너트 누락
- 와셔 누락
- 두 개 이상의 부품 누락
- 잘못된 부품 투입
- 제품 자체가 없는 경우

검사 대상과 방식은 데이터 수집 난이도와 촬영 환경을 확인한 후 변경할 수 있다.

# 4. 프로젝트의 핵심 원칙

## 4.1 AI가 중심이다

이 프로젝트에서 가장 중요한 것은 WPF 화면을 예쁘게 만드는 것이 아니다.

핵심은 다음 과정이다.

1. 직접 검사 문제를 정의한다.
2. 직접 이미지를 수집한다.
3. 직접 라벨링한다.
4. 사전학습된 YOLO 모델을 파인튜닝한다.
5. 검증 데이터로 성능을 확인한다.
6. 실패 사례를 분석한다.
7. 데이터를 보완하여 다시 학습한다.
8. 실제 촬영 환경에서 동작하는지 확인한다.
9. 모델 결과를 검사 프로그램과 연결한다.

WPF, FastAPI, Microsoft SQL Server은 AI 모델이 실제로 사용되는 과정을 보여주기 위한 도구다.

## 4.2 실제 공장 전체를 구현하지 않는다

이번 프로젝트는 스마트팩토리 전체 구현이 아니라 **AI 검사 장비 한 대의 소프트웨어를 축소 구현하는 프로젝트**다.

따라서 다음 항목은 1차 범위에서 제외한다.

- 실제 PLC
- 실제 아두이노
- 실제 컨베이어 벨트
- 실제 산업용 카메라
- 로봇암
- Unity 기반 3D 공장
- Factory I/O 전체 시뮬레이션
- C++ 기반 추론
- 본격적인 MES
- 클라우드 배포
- 복잡한 사용자 권한 관리

## 4.3 먼저 완성하고 이후 고도화한다

1차 완성 구조는 다음과 같다.

```text
WPF
  ↓ HTTP 이미지 전송
FastAPI
  ↓
Python YOLO 모델 추론
  ↓
Microsoft SQL Server 저장
```

시간이 충분히 남을 때만 다음 고도화를 고려한다.

```text
Python에서 YOLO 학습
  ↓
ONNX 형식으로 변환
  ↓
C# WPF에서 ONNX Runtime으로 직접 추론
```

처음부터 ONNX를 적용하면 C#에서 이미지 전처리, Tensor 변환, 모델 출력 후처리, NMS 등을 직접 구현해야 하므로 일정이 크게 늘어날 수 있다.

# 5. 전체 시스템 흐름

```text
1. 작업자가 검사할 조립 트레이를 웹캠 앞에 배치한다.

2. WPF 프로그램에서 [검사 시작] 버튼을 누른다.

3. WPF가 현재 웹캠 이미지를 캡처한다.

4. WPF가 이미지를 FastAPI 서버로 전송한다.

5. FastAPI가 YOLO 모델을 이용해 볼트·너트·와셔를 탐지한다.

6. 필수 부품 목록과 실제 탐지 결과를 비교한다.

7. 모든 필수 부품이 존재하면 OK로 판정한다.

8. 일부 부품이 없으면 NG로 판정하고 누락 부품을 기록한다.

9. FastAPI가 검사 결과와 검사 이미지를 저장한다.

10. 검사 결과를 Microsoft SQL Server에 저장한다.

11. FastAPI가 WPF에 JSON 형식으로 결과를 반환한다.

12. WPF가 바운딩 박스, 탐지 결과, OK·NG, 누락 부품을 화면에 표시한다.

13. 사용자는 [다음 제품] 버튼을 눌러 다음 검사로 넘어간다.

14. 검사 이력 화면에서 날짜·판정 결과별로 조회한다.

15. [Excel 내보내기] 버튼으로 검사 결과를 .xlsx 파일로 추출한다.
```

### 라벨 클래스 예시

```text
bolt
nut
washer
```

`normal`, `defect`만 라벨링하는 것보다 실제 부품 이름을 클래스로 지정하는 것이 좋다.

YOLO는 부품을 탐지하고, 최종 정상·불량 판정은 별도의 검사 규칙이 담당한다.

```python
required_parts = {"bolt", "nut", "washer"}
detected_parts = {"bolt", "nut"}

missing_parts = required_parts - detected_parts

if missing_parts:
    result = "NG"
else:
    result = "OK"
```

### Microsoft SQL Server를 선택한 이유

SQLite는 단일 PC에서 독립적으로 실행되는 검사 프로그램의 로컬 저장소로 충분히 사용할 수 있다.

Microsoft SQL Server와 PostgreSQL은 모두 여러 프로그램이 접속할 수 있는 서버형 관계형 데이터베이스이므로, 이번 프로젝트에 필요한 검사 결과 저장·검색·통계·Excel 추출 기능은 어느 쪽으로도 구현할 수 있다.

그럼에도 이번 프로젝트에서는 다음 이유로 Microsoft SQL Server를 선택한다.

- C#·.NET·WPF 기반 제조 소프트웨어와 기술 생태계가 잘 맞는다.
- 스마트팩토리, MES, 검사장비 소프트웨어에서 자주 보이는 C#·WPF·MSSQL 조합을 경험할 수 있다.
- SSMS를 이용해 데이터베이스, 테이블, 데이터, SQL 실행 결과를 직접 확인할 수 있다.
- 서버형 데이터베이스의 접속 계정, 권한, 연결 문자열과 중앙 저장 구조를 경험할 수 있다.
- FastAPI에서도 SQLAlchemy와 pyodbc를 이용해 연결할 수 있다.
- 여러 검사 프로그램이나 관리 프로그램이 하나의 중앙 DB를 함께 사용하는 구조로 확장할 수 있다.
- SQL Server의 T-SQL과 Microsoft 데이터베이스 관리 도구를 학습할 수 있다.

SQL Server를 사용한다고 AI 모델 성능이 올라가는 것은 아니다. 프로젝트의 중심은 여전히 데이터 수집, YOLO 파인튜닝, 실패 사례 분석과 모델 개선이다.

DB는 AI 검사 결과를 실제 업무 데이터로 누적하고 조회하는 역할을 맡는다.

### 프로젝트에서 사용할 에디션

개발과 포트폴리오 목적이므로 다음 중 하나를 사용한다.

- **SQL Server Developer Edition:** 개발·테스트 목적으로 무료이며 SQL Server 기능 학습에 적합
- **SQL Server Express Edition:** 무료이며 소규모 애플리케이션에 적합하지만 일부 자원 제한이 있음

처음에는 Windows 노트북에 **SQL Server Developer Edition과 SSMS를 로컬 설치**하는 방향을 우선한다.

Docker 기반 SQL Server 실행은 1차 필수 범위에서 제외하고, 프로젝트 완료 후 컨테이너화가 필요할 때 선택적으로 진행한다.

### FastAPI 연결 구조

```text
WPF
  ↓ HTTP
FastAPI
  ↓ SQLAlchemy
pyodbc + Microsoft ODBC Driver
  ↓
Microsoft SQL Server
```

WPF가 SQL Server에 직접 접속하지 않고, FastAPI가 검사 결과 저장과 조회를 전담하도록 구성한다.

| 구성 | 역할 |
|---|---|
| WPF | 검사 화면과 사용자 조작 |
| FastAPI | AI 추론, 검사 규칙, DB 저장과 조회 |
| Microsoft SQL Server | 검사 이력의 중앙 저장 |
| YOLO | 볼트·너트·와셔 탐지 |

```python
product_id = "P-001"
```

```csharp
string productId = "P-001";
```

## 8.3 WPF란?

WPF는 **Windows Presentation Foundation**의 약자다.

```text
Axios           ↔           HttpClient

데이터 연결      ↔           Data Binding
```

다만 Vue는 브라우저에서 실행되고, WPF는 Windows에서 `.exe` 프로그램으로 실행된다.

# 9. 데이터베이스와 ORM 이해

## 9.1 ORM이란?

ORM은 Object Relational Mapping의 약자다.

Python 클래스와 데이터베이스 테이블을 연결해주는 기술이다.

```text
Python 클래스
    ↕ ORM
SQL Server 테이블
```

예를 들어 다음 Python 객체를 저장하면,

```python
inspection = Inspection(
    product_id="P-001",
    result="NG",
    confidence=0.91,
)
```

ORM이 내부적으로 SQL을 만들어 실행한다.

```sql
INSERT INTO inspections (
    product_id,
    result,
    confidence
)
VALUES (
    'P-001',
    'NG',
    0.91
);
```

ORM을 사용해도 DB 지식이 필요 없다는 뜻은 아니다.

이번 프로젝트에서는 최소한 다음 SQL을 이해한다.

- SELECT
- INSERT
- UPDATE
- DELETE
- WHERE
- ORDER BY
- GROUP BY
- JOIN

ORM 코드가 실제로 어떤 SQL과 연결되는지 확인하며 학습한다.

# 10. 데이터베이스 설계 초안

## 10.1 핵심 테이블

### inspections

| 컬럼 | SQL Server 타입 예시 | 설명 |
|---|---|---|
| id | BIGINT IDENTITY(1,1) | 검사 고유 번호, 자동 증가 |
| product_id | NVARCHAR(100) | 제품 번호 |
| inspected_at | DATETIME2 | 검사 시간 |
| result | NVARCHAR(10) | OK / NG |
| defect_type | NVARCHAR(100) | 누락 또는 불량 유형 |
| detected_parts | NVARCHAR(MAX) | 탐지된 부품 정보를 JSON 문자열로 저장 |
| missing_parts | NVARCHAR(MAX) | 누락된 부품 목록을 JSON 문자열로 저장 |
| confidence | FLOAT | 대표 신뢰도 |
| inference_ms | INT | 추론 시간 |
| model_version | NVARCHAR(50) | 사용한 모델 버전 |
| original_image_path | NVARCHAR(500) | 원본 이미지 경로 |
| result_image_path | NVARCHAR(500) | 바운딩 박스 결과 이미지 경로 |
| created_at | DATETIME2 | DB 생성 시각 |

처음에는 하나의 테이블로 시작한다.

시간이 남으면 다음 테이블을 분리할 수 있다.

- models
- defect_types
- products
- detections
- users

하지만 1차 프로젝트에서는 과도한 DB 설계를 하지 않는다.

PostgreSQL의 `JSONB`와 달리 SQL Server에서는 동일한 이름의 전용 JSON 자료형을 사용하지 않는다. 초기 버전에서는 `detected_parts`와 `missing_parts`를 `NVARCHAR(MAX)`에 JSON 문자열로 저장한다.

예시:

```json
{
  "detected_parts": [
    {"name": "bolt", "confidence": 0.94},
    {"name": "nut", "confidence": 0.91}
  ],
  "missing_parts": ["washer"]
}
```

시간이 남고 관계형 설계를 더 명확히 보여주고 싶다면 탐지 결과를 `inspection_detections`와 같은 별도 테이블로 분리한다.

## 13.2 데이터 분리

데이터를 다음과 같이 분리한다.

- Train
- Validation
- Test

중요한 원칙:

같은 촬영 영상에서 연속으로 뽑은 매우 비슷한 이미지가 Train과 Test에 동시에 들어가지 않도록 한다.

가능하면 촬영 날짜나 촬영 세션을 기준으로 분리한다.

예시:

```text
1일차 촬영: Train

3일차 촬영: Test
```

## 13.3 평가 지표

최소한 다음을 확인한다.

- Precision
- Recall
- mAP@50
- mAP@50:95
- Confusion Matrix
- 클래스별 성능
- 추론 시간
- 실제 웹캠 테스트 성공률

### Precision

모델이 탐지했다고 판단한 것 중 실제로 맞은 비율이다.

높을수록 불필요한 오탐이 적다.

### Recall

실제로 존재하는 부품 중 모델이 찾아낸 비율이다.

비전 검사에서는 부품 누락이나 불량을 놓치는 것이 큰 문제가 될 수 있으므로 Recall이 중요하다.

### 추론 시간

생산라인 속도에 맞춰 결과가 나와야 하므로 정확도뿐 아니라 처리 시간도 함께 기록한다.

---

## 13.4 실패 사례 분석

프로젝트에서 가장 중요한 부분 중 하나다.

예시:

```text
문제:
은색 와셔와 밝은 배경의 색이 비슷할 때 와셔 탐지 실패

원인 추정:
배경과 부품의 명암 차이가 작고 학습 데이터가 부족함

개선:
어두운 배경과 다양한 조명 조건의 이미지를 추가 수집

결과:
와셔 클래스 Recall 개선
```

```text
문제:
볼트와 너트가 겹칠 때 너트를 놓침

개선:
겹침 상황 데이터를 추가하고 재학습
```

단순히 최종 정확도만 보여주는 것이 아니라, 실패 → 원인 분석 → 데이터 보완 → 재학습 과정을 보여준다.

# 16. 개발 장비와 AI 학습 환경 운영 전략

## 16.1 현재 사용할 장비

프로젝트 개발에 사용할 주 장비는 Windows 노트북이다.

노트북 사양은 다음과 같다.

- CPU: Intel Core Ultra 5 228V
- 메모리: 32GB
- 저장장치: 1TB SSD
- 그래픽: Intel Arc 내장 그래픽

따라서 프로젝트에서는 장비 역할을 다음과 같이 나눈다.

```text
Windows 노트북

- 소규모 학습 테스트

- YOLO 추론

- 최종 시연

Google Colab
- YOLO 본 학습
- 여러 Epoch 학습
- 모델 버전 비교
- 데이터 증강 실험
- 하이퍼파라미터 실험

```

## 16.2 노트북으로 YOLO 학습이 가능한가?

기술적으로는 가능하다.

Ultralytics YOLO는 GPU가 없는 환경에서도 CPU를 이용해 학습할 수 있다.

예시:

```python
model.train(
    data="data.yaml",
    epochs=2,
    imgsz=320,
    batch=2,
    device="cpu",
)
```

하지만 CPU 학습은 다음과 같은 확인 용도로만 사용한다.

- 데이터 경로가 올바른지 확인
- 라벨 형식이 올바른지 확인
- 클래스 이름이 일치하는지 확인
- 학습 코드가 정상 실행되는지 확인
- 1~3 Epoch 정도의 소규모 테스트
- 작은 이미지 크기로 빠른 오류 확인

본 학습을 CPU로 진행하면 데이터 수와 Epoch가 늘어날수록 시간이 크게 증가한다.

따라서 노트북에서는 학습 가능 여부를 검증하는 정도로만 사용하고, 실제 파인튜닝은 Google Colab의 NVIDIA GPU를 사용한다.

---

## 16.3 노트북의 32GB 메모리를 이해할 때 주의할 점

노트북에 32GB 메모리가 있어도 이것이 32GB의 전용 GPU 메모리를 의미하지는 않는다.

외장 GPU가 있는 PC는 보통 다음처럼 메모리가 분리된다.

```text
CPU용 시스템 RAM
+
GPU 전용 VRAM
```

현재 노트북은 내장 그래픽을 사용하므로 CPU와 GPU가 시스템 메모리를 공유한다.

따라서 모델 학습 가능 여부는 단순히 메모리 용량만으로 결정되지 않는다.

다음 요소가 함께 영향을 준다.

- GPU 연산 성능
- 메모리 대역폭
- 딥러닝 프레임워크 최적화
- 냉각 성능
- 지속 전력
- 모델 크기
- 이미지 크기
- Batch Size

노트북의 32GB 메모리는 WPF, FastAPI, Microsoft SQL Server, 데이터 처리, 모델 추론 등을 동시에 실행하는 데에는 유리하지만, NVIDIA 외장 GPU를 대체하는 학습 자원으로 볼 수는 없다.

---

## 16.4 Intel 내장 GPU와 NPU는 어떻게 활용할까?

Intel Arc 내장 GPU와 NPU는 AI 연산을 지원하지만, 이번 프로젝트에서는 본 학습 장치로 사용하지 않는다.

이유는 다음과 같다.

- 대부분의 YOLO 학습 자료가 NVIDIA CUDA 기준이다.
- Intel GPU 학습 환경은 별도 드라이버와 PyTorch XPU 구성이 필요하다.
- 패키지 호환 문제를 해결하는 데 시간이 들어갈 수 있다.
- 프로젝트 기간이 짧아 환경 설정 자체가 목적이 되어서는 안 된다.
- NPU는 일반적으로 모델 학습보다 추론에 더 적합하다.

따라서 Intel GPU와 NPU는 선택적인 고도화 단계에서 추론 최적화 용도로 검토한다.

예상 고도화 흐름:

```text
Google Colab에서 YOLO 학습
        ↓
best.pt 생성
        ↓
OpenVINO 형식으로 변환
        ↓
Intel CPU / GPU / NPU에서 추론
        ↓
장치별 추론 시간 비교
```

이 고도화는 1차 프로젝트를 완성한 후 시간이 남을 때만 진행한다.


학습은 Colab에서 수행하지만, 최종 모델이 실제 노트북에서 정상적으로 추론되는지는 반드시 확인한다.

이번 프로젝트는 버튼을 눌러 한 장씩 검사하는 반자동 구조이므로, 처음부터 실시간 30FPS를 목표로 하지 않는다.

초기 목표는 사용자가 검사 버튼을 누른 뒤 불편하지 않은 시간 안에 결과가 표시되는 것이다.

실제 추론 시간은 다음 항목과 함께 측정한다.

- 이미지 크기
- 모델 크기
- CPU 추론 시간
- 전처리 시간
- 모델 추론 시간
- 후처리 시간
- 전체 API 응답 시간

## 16.7 모델 크기 선택

처음에는 가장 작은 Nano 계열 모델로 전체 파이프라인을 완성한다.

```text
1차:
Nano 모델로 데이터 학습과 전체 시스템 연결

2차:
데이터 품질 개선 및 Nano 재학습

3차:
필요한 경우 Small 모델과 성능 비교

4차:
정확도 향상과 추론 속도 저하의 trade-off 분석
```

처음부터 큰 모델을 사용하면 다음 문제가 생길 수 있다.

- 학습 시간 증가
- 추론 시간 증가
- 노트북 CPU 추론 부담 증가
- 반복 실험 횟수 감소
- 전체 시스템 통합 지연

볼트·너트·와셔처럼 비교적 형태가 명확한 객체는 작은 모델로도 충분한 성능이 나올 가능성이 있다.

따라서 우선 데이터 품질과 실패 사례 개선에 집중한다.

## 16.8 데이터 규모의 초기 목표

정확한 수량은 검사 난이도와 촬영 다양성에 따라 달라질 수 있다.

초기 목표는 다음과 같이 잡는다.

```text
기능 확인:
200~300장

1차 모델:
500~1,000장

조건 다양화 후:
1,000~2,000장
```

이미지 수보다 중요한 것은 데이터 다양성이다.

다음 상황을 포함한다.

- 조명 변화
- 회전
- 거리 변화
- 배경 변화
- 부품 위치 변화
- 부품 겹침
- 각 누락 유형
- 빈 트레이
- 유사한 다른 물체

연속 영상에서 거의 동일한 프레임을 대량으로 추출하기보다, 서로 다른 상황을 포함한 데이터를 확보한다.

# 25. 새로운 채팅방에서 사용할 초기 메시지

아래 내용을 새로운 ChatGPT 프로젝트 또는 채팅방에 붙여넣으면 현재 계획을 이어서 진행할 수 있다.

```text
나는 AI 비전 검사 직무 취업을 목표로 약 6주 동안 1인 포트폴리오 프로젝트를 진행하려고 한다.

프로젝트는 웹캠으로 볼트·너트·와셔가 들어 있는 조립 트레이를 촬영하고, 직접 수집·라벨링한 데이터로 YOLO 모델을 파인튜닝하여 부품 누락 여부를 검사하는 시스템이다.

프로젝트의 중심은 WPF가 아니라 AI 모델 튜닝과 개선 과정이다.

전체 구성은 다음과 같다.

- AI: Python, PyTorch, Ultralytics YOLO, OpenCV
- Desktop UI: C#, .NET, WPF, XAML
- AI/Backend API: FastAPI
- DB: Microsoft SQL Server(MSSQL)
- DB 관리 도구: SQL Server Management Studio(SSMS)
- DB 연결: pyodbc, Microsoft ODBC Driver 18 for SQL Server
- ORM: SQLAlchemy
- Migration: Alembic
- Excel: pandas, openpyxl
- 웹캠 연결: OpenCvSharp 또는 적절한 C# 카메라 라이브러리

전체 흐름은 다음과 같다.

1. WPF에서 검사 시작
2. 웹캠 이미지 캡처
3. FastAPI로 이미지 전송
4. YOLO가 볼트·너트·와셔 탐지
5. 필수 부품과 탐지 결과 비교
6. OK 또는 NG 판정
7. 검사 결과와 이미지 경로를 Microsoft SQL Server에 저장
8. WPF에 결과 표시
9. 검사 이력 조회
10. 날짜·결과별 Excel 추출

실제 PLC, 아두이노, 컨베이어, Unity, C++는 1차 범위에서 제외한다.

6주 계획은 다음과 같다.
```
